Relatório de execução

O que aconteceu nesta execução

npm run dev abria uma janela do Electron em vez do browser, e a janela mostrava só o texto cru da tela de configuração. Eram duas causas independentes. Foram 13 sub-agentes em 6 ondas, e a primeira prova visual que este repositório já teve.

v3.2.0 09/08/2026 main run 20260809-013142-2852240

O pedido

“arrume a aplicação: quando rodo npm run dev ela abre uma janela própria em vez de abrir a URL no browser, e não renderiza nada da nossa interface — aparece só ‘Bem-vindo ao Explainer / Configure sua chave da OpenAI para começar / OPENAI_API_KEY / sk-… / Configurações avançadas / Validar e Salvar / Onde encontro minha chave? / Pular configuração’. Só entregue quando tiver arrumado, teste e valide, muitos subagents para deixar tudo perfeito.”

Esse texto que o usuário colou não é um erro genérico: é literalmente o conteúdo de frontend/src/components/SetupScreen.tsx renderizado sem uma única regra de CSS aplicada. Foi o sintoma que apontou para a segunda causa.

As duas causas raiz

Elas são independentes. Corrigir uma sem a outra deixaria metade da queixa de pé.

Causa AAbria janela em vez de browser

O package.json da raiz tinha "dev": "electron-vite dev". Rodar npm run dev subia o Electron — o contrário do que README.md e AGENTS.md descreviam havia commits, e a queixa literal do usuário.

Corrigida em 013c98b (onda1-dev-browser).

Causa BNenhuma regra de CSS chegava na tela

O bloco renderer do electron.vite.config.ts declarava plugins: [react()] e mais nada. O frontend é Tailwind v4 via @tailwindcss/vite, e o Tailwind v4 não tem etapa PostCSS de reserva: sem o plugin, o CSS emitido eram 66 kB de FONTE não compilada — @theme default{…}, o literal @tailwind utilities;, três @apply crus — que o browser lê e descarta inteiro.

Corrigida em dbaab96 (onda1-renderer-pipeline).

Por que exatamente aquele texto: descartado o CSS inteiro, o que sobra na tela é o DOM cru da primeira coisa que o app renderiza — a tela de setup. Título, rótulo do campo, placeholder sk-…, os dois links e o botão, um embaixo do outro, sem estilo. É a lista que o usuário colou, na ordem em que ele colou.

O SetupScreen tinha quatro becos sem saída, não um

O usuário relatou o primeiro. Os outros três estavam ali do mesmo jeito.

1
A chave salva e validada voltava como não-configurada — em todo boot, para sempre.

A tela exigia validationStatus === "valid" para considerar a chave configurada. Mas electron/main/ipc/settings-handlers.ts persiste 'idle', e nada no main process jamais escreve 'valid' — os únicos literais no código do main são 'idle' (settings-store.ts, linhas 63, 64, 185 e 395).

Regra nova: saved?.key && saved.validationStatus !== "invalid" — existe chave e ela não foi marcada inválida.

2
Carregando para sempre, sem erro.

ipcRenderer.invoke num canal não registrado nunca resolve nem rejeita. O catch que existia não pegava nada, porque não havia rejeição para pegar.

SETTINGS_READ_TIMEOUT_MS = 4000 degrada para o app. Quem já chegou ao formulário não é arrancado dele.

3
Uma ponte parcial passava por ponte boa.

window.api.isElectron sozinho não prova nada: o exposeInMainWorld do preload roda dentro de um try. hasSetupBridge passou a exigir os métodos que a tela realmente chama — getApiKey, saveApiKey, validateApiKey e app.openExternal.

Ponte parcial é ponte nenhuma, e o caminho do browser renderiza o app.

4
O auto-avanço de 1 s podia nunca chegar.

onComplete chegava como uma arrow nova a cada render do App, e cada re-render do pai reiniciava o timer. Um pai que re-renderiza mais rápido que o timeout adiava a entrega indefinidamente.

Estabilizado via useCallback; a decisão passou a viver no módulo (isSetupDismissed), fora do ciclo de render.

O gate do App.tsx, antes e depois

Antes
const [setupComplete, setSetupComplete] = useState(false);
const isElectron =
  typeof window !== "undefined" && window.api?.isElectron === true;

// …
if (isElectron && !setupComplete) {
  return <SetupScreen onComplete={() => setSetupComplete(true)} />;
}
Depois
const [setupDismissed, setSetupDismissed] = useState(isSetupDismissed);
const completeSetup = useCallback(() => setSetupDismissed(true), []);
const showSetup = shouldShowSetup({
  bridge: electronBridge(),
  dismissed: setupDismissed,
});

// …
if (showSetup) {
  return <SetupScreen onComplete={completeSetup} />;
}

A regra virou uma função pura, escrita uma vez, que o chamador e o teste leem igual.

As mutações — o que separa um smoke real de um que passaria com página em branco

Um smoke que ninguém viu falhar é um smoke em que ninguém deveria confiar. Os dois foram rodados de propósito contra o bug de volta:

Mutação 1--mutate=electron-bridge

Injeta um window.api completo na página antes dela carregar — a forma exata que encalhava o build de desktop na tela de setup.

Resultado: exit 1, e só a asserção 2 falha: “tela de setup no ar”. Reproduz o bug original.

Mutação 2--mutate=raw-css

Troca todas as folhas de estilo pelo CSS-fonte não compilado — byte a byte o que o renderer recebia antes da onda 1.

Resultado: exit 1, e só a asserção 3 falha:

main.display        = block
mic.display         = inline-block
mic.width           = 40px
mic.border-radius   = 0px
shell.background    = rgba(0, 0, 0, 0)

A captura da rodada da mutação 2 é o “só texto cru” que o usuário reclamou. Cada mutação derruba exatamente uma asserção e nenhuma outra — o que prova que as asserções são independentes e que nenhuma delas está passando por acidente.

A mesma disciplina valeu para o resto da execução:

  • Gate do SetupScreen: inverter para if (!showSetup) quebra 4 casos; trocar por return null (janela branca) quebra 2; afrouxar o guard da ponte quebra 2. O teste de grep textual que existia antes sobrevivia aos três.
  • Gate estendido: reverter a linha do moduleResolution mata o gate na seção TypeCheck Root; quebrar o teste de electron mata na seção Test Desktop. Restaurado com md5sum conferido.
  • Auto-open: provado com um xdg-open falso no PATH, e o bug de porta reproduzido com um squatter servindo <h1>APP DE OUTRA PESSOA</h1> na 5173.

Ganhos de tabela

Renderer minificado

O electron-vite usa minify:false como padrão do renderer e o bloco nunca sobrescrevia. out/renderer caiu de 8.200.635 para 4.212.085 bytes (−48,6%); o index.js, de 1.412.227 para 622.867 (−55,9%), com keepNames verificado.

Backend que existe

Em dev o main process apontava para backend/dist/index.js, que só existe depois de um build. Agora roda tsx watch src/index.ts, em paridade com o dev.sh, e reusa um backend já vivo na 3001 em vez de brigar pela porta.

Portas honestas

O Vite ganhou strictPort, e o dev.sh classifica 5173 e 3001 antes de gerar processo. A sonda deixou de ser socket cru e virou identidade: GET /@vite/client exigindo 200 com content-type de JavaScript.

Gate com alcance

Os 14 testes de electron/main/services existiam desde a onda 1 e nenhum comando do repositório os alcançava. Agora validate.sh typecheca os quatro projetos, roda a suíte do desktop e faz o build do desktop.

Documentação alcança o desktop

README.md e AGENTS.md ganharam o caminho desktop, a tabela de scripts e — o que importa mais — a limitação conhecida do npm run dist. Critério provado por diferença de conjuntos: todo npm run X citado existe no package.json.

Skill que parou de mentir

verifying-explainer-changes afirmava que React não podia ser renderizado na suíte. Enquanto dizia isso, agentes escolhiam um sinal mais fraco que o disponível — foi exatamente o que aconteceu com o primeiro teste do gate. Evals de 6 para 12 casos.

Premissas assumidas sem perguntar

O orquestrador operou em autonomia total: nenhuma pergunta foi feita. Toda premissa fica registrada aqui.
