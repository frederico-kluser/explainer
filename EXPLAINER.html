1. Sinalizacao do modo ativo (frontend)

Antes
  • O modo de cada conversa (conversation/presentation/research) existia so como dado interno: o App resolvia activeMode para documento/needsMaterial, mas NENHUM lugar da UI mostrava em que modo o usuario esta. Conversas na lista eram indistinguiveis (icone MessageSquare generico).
Depois
  • Badge com icone + label do modo: header do chat no desktop (row de status ao vivo e acima do seletor de material antes da chamada), barra superior no mobile, icone do modo em CADA conversa da lista (sidebar e drawer) com tooltip "Conversa · <label>", e hint "<label> · Atualizada ..." na command palette.

2. Robustez (conversas legadas e modos desconhecidos)

Antes
  • Sem caminho de exibicao — nada a degradar.
Depois
  • Conversas criadas antes dos modos (sem metadata.mode) continuam com o icone generico MessageSquare byte-a-byte; modo desconhecido cai no allowlist com fallback Sparkles; conversa legada mostra o primeiro modo do registro no header (mesma regra do servidor, getMode); sem conversa ativa, nenhum badge fantasma (gate activeMode && activeConversation).

3. Estrutura de codigo

Antes
  • Allowlist de icones era constante privada do ModePicker — impossivel reutilizar para badges.
Depois
  • mode-icons.ts compartilhado (MODE_ICONS + resolveModeIcon); ModeBadge reutilizavel (xs/sm); props novas opcionais (mode, modesById) — servidor/cliente antigo nao quebra; backend intocado.

4. Cobertura de testes

Antes
  • 502 testes frontend; caminho mobile do App nunca exercitado (happy-dom matchMedia false → compact=false sempre).
Depois
  • 511 testes frontend (22 novos): caminho mobile real no App via stub de matchMedia + cache de modulo do use-compact-layout; fallback modes[0] do registro com MUTATION CHECK (remover o fallback derruba exatamente os testes novos); palette aberta pelo trigger real com portal; estado transiente (modes carregando).

Premissas inferidas sem perguntar

O orquestrador opera em autonomia total: nenhuma pergunta foi feita ao usuário. Toda premissa assumida fica registrada aqui — para revisão e reprodutibilidade.

  • O seletor ja existia: o pedido "um seletor quando clico em nova conversa" ja estava atendido (botao Nova conversa abre o ModePicker com os 3 modos e comunica congelamento). A entrega focou na sinalizacao — e o revisor de plano confirmou que reforco adicional seria gold-plating.
  • Sinalizacao em 4 superficies: header desktop (2 estados), topbar mobile, lista de conversas (2 instancias de Sidebar), command palette — nenhuma superfície onde conversas sao vistas ficou sem o modo.
  • Allowlist compartilhada: mode-icons.ts extraido do ModePicker (mesma filosofia de seguranca: nome da wire nunca vira componente direto; fallback Sparkles).
  • Sem badge fantasma: gate em activeMode && activeConversation — activeMode cai em modes[0] mesmo sem conversa; o install vazio nao mostra modo nenhum.
  • Conversas legadas intactas: sem metadata.mode → MessageSquare byte-a-byte (mesmas classes, mesmo tooltip); props novas opcionais (cliente/servidor antigo nao quebram).
  • Backend intocado: zero mudancas fora de frontend/src — a sinalizacao e derivada de dados que ja existiam (GET /api/modes e metadata.mode).
  • Prova por mutacao: o teste do fallback do registro foi validado removendo ?? modes[0] temporariamente — exatamente os 2 testes novos falham; a regressao descrita pela revisao nao passa mais.
